## 9.4 渠道集成为 Phase 8（后续迭代）

消息渠道模块 `openharness-channels` 涉及 10 个第三方平台的 SDK 集成（飞书、Slack、Discord、Telegram、钉钉、Email、QQ、Matrix、WhatsApp、Mochat），工作量约 4 周。由于：
1. 依赖大量第三方 Java SDK（部分无 Java 等价 SDK，需直接封装 HTTP API）
2. 需要各平台开发者账号和测试沙箱环境
3. 与核心 Agent 能力无关，属于分发层

MVP 不交付渠道集成（建议作为 Phase 8 迭代），但 MessageBus、ChannelBridge 抽象接口在设计文档中保留，供后续实现。

# 十一、风险与缓解

|风险|影响|缓解措施|
|---|---|---|
|SSE 流式解析兼容性|API 客户端无法正确解析部分提供商的 SSE 格式|使用成熟的 SSE 库（okhttp-sse），编写针对每个提供商的集成测试|
|前端协议偏移|Java 后端与 TypeScript 前端 JSON 格式不一致|建立 JSON Schema 契约测试，每次变更自动验证所有 17 种 BackendEvent|
|Python 生态独有依赖|部分 Python SDK（如 lark-oapi）无 Java 等价|优先使用 REST API 直接调用，自行封装 HTTP 客户端|
|Virtual Threads 与第三方库兼容|部分库在 Virtual Thread 上有 pinning 问题|使用 `-Djdk.tracePinnedThreads=full` 监控，必要时回退到平台线程池|
|性能回归|Java 启动时间较 Python 长|使用 GraalVM native-image 或 CDS（Class Data Sharing）加速启动|
|工具系统差异|44 个工具的行为需逐一对齐|复用原版 E2E 测试场景，逐工具验证输出一致性|
|Token 计数精度|Java 无 tiktoken 等价库，字符/4 启发式有偏差|默认使用 API 返回的 usage 字段（权威值）；可选集成 Jtokkit 精确离线计数|
|JSON-Lines 协议兼容性|Jackson 序列化与 TypeScript 类型不完全对齐|使用 `@JsonTypeInfo` 多态注解对齐 type 字段名和值；契约测试自动化|
|MCP 协议版本变更|MCP 协议升级导致客户端不兼容|使用 MCP Java SDK 封装，隔离协议变动范围|
|Kaniko/镜像构建|Docker 镜像构建需要 Docker daemon 或 Kaniko|使用 Jib Maven Plugin 实现无 daemon 构建|
|内存记忆规模膨胀|大量记忆文件导致搜索性能下降|签名去重 + TTL 过期 + 重要性评分；使用 SQLite FTS 作为可选后端|
|Swarm 子进程泄漏|子进程异常退出未清理导致僵尸进程|CompletableFuture.allOf() + Process.waitFor() + atexit 注册|

# 十二、性能优化策略

|优化项|策略|预期收益|
|---|---|---|
|启动加速|GraalVM native-image/Spring AOT/CDS|启动时间＜1s|
|内存优化|对话消息使用 compact record、大文件流式处理|内存占用降低30％|
|并发优化|Virtual Threads 替代线程池、CompletableFuture 并行编排|支持1000＋并发工具执行|
|序列化优化|Jackson AfterburnerModule/Blackbird|JSON处理提速30％|
|IO 优化|NIO Channel＋零拷贝|大文件读写提速|
|缓存优化|Caffeine 本地缓存（技能／配置／提供商解析）|重复查询延迟＜1ms|

# 十三、总结

本方案完整覆盖了 OpenHarness 的 **11 个 Maven 模块**，按功能域合并后包括：

- **核心基础设施**（4 模块）：common（共享类型）、config（配置系统）、api（LLM 客户端 + 认证）、engine（Agent Loop + 权限）
- **工具系统**（1 模块）：tools（44 个内置工具 + MCP 动态工具）
- **扩展系统**（1 模块）：extensions（hooks、skills、plugins、commands、mcp、memory、coordinator、tasks、swarm、services、bridge、personalization、autopilot、state、keybindings、themes、vim、voice、utils）
- **UI + CLI**（2 模块）：ui（JSON-Lines 协议层）、cli（Picocli 入口）
- **可观测性 + 代理层 + 打包**（3 模块）：observability（Metrics/Tracing/Logging）、ohmo（Gateway、Workspace、Router）、app（Fat JAR）

核心设计决策：

1. Java 21 Virtual Threads 替代 Python asyncio，保持异步模型简洁
2. Sealed Interface 替代 Python Union 类型，保持类型安全
3. Jackson + Jakarta Validation 替代 Pydantic，保持数据校验能力
4. Picocli 替代 Typer，保持 CLI 体验一致
5. 前端零改动，通过 JSON-Lines 协议兼容实现后端无缝切换
6. OpenTelemetry + Micrometer + Logback 三位一体可观测性，生产就绪（原 Python 版无此能力）
7. 字符/4 启发式 Token 估算，零依赖对齐 Python 实现
8. 消息渠道（10 个平台）在 Python 版已完整实现；Java 版因第三方 SDK 依赖较多，建议作为 Phase 8 迭代，但核心抽象（MessageBus、ChannelBridge）已在架构中预留

MVP 11 模块，预计 450+ Java 文件，250+ 测试用例，核心引擎闭环建议 3-4 个月，完整复刻预计 9-12 个月。

> **渠道集成说明**：消息渠道（飞书/Slack/Discord/Telegram/钉钉/Email/QQ/Matrix/WhatsApp/Mochat）在 Python 版 `src/openharness/channels/` 中已完整实现。Java 版涉及大量第三方 SDK 集成（部分平台无成熟 Java SDK），建议作为独立 Phase 实施（约 4 周），但 ChannelBridge、MessageBus 等抽象已在架构中预留。
>
> **ohmo 说明**：`ohmo/` 是构建在 OpenHarness Core 之上的个人 AI Agent 应用（约 6300 行 Python，19 个文件），包含 Gateway 服务、个人工作空间（`~/.ohmo`）、会话路由、ohmo 人格提示词等。若仅需复刻 OpenHarness Core CLI 框架，可裁剪此模块。

> **token 估算说明**：Java 版本默认使用与 Python 版相同的字符/4 启发式算法（`max(1, (len(text) + 3) / 4)`），零额外依赖。精确计数使用 API 返回的 usage 字段。需要离线精确计数的场景可选集成 Jtokkit 库。
