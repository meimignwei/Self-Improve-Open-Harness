## 五、行为等价性验证方案

"100% 行为级复刻"必须有可操作的验证手段。以下四层验证从细粒度到端到端，逐层收敛。

### 5.1 第一层：工具级输入输出对（每个工具）

**目标**：43 个工具逐一验证，同输入 → 同输出。

**方法**：
1. 对每个工具，从 Python 源码中提取典型输入参数组合（正常路径 + 至少 2 个边界/错误路径）。
2. 在相同文件系统状态下，分别调用 Python 版和 Java 版工具，捕获 `ToolResult`。
3. 对比 content 文本（允许时间戳/临时路径等 Volatile 字段差异）、isError 标志、mediaFiles 列表。
4. 不一致的 case 生成 diff 报告，归类为：Java 缺陷 / Python 缺陷 / 有意差异 / 无法消除的环境差异。

**产出**：`tests/equivalence/tools/` 下每个工具一个 JSON 测试夹具文件 `{tool_name}_cases.json`，格式：

```json
{
  "tool": "bash",
  "cases": [
    {
      "id": "bash_001_echo",
      "input": {"command": "echo hello", "timeout_ms": 5000},
      "expected": {
        "content": "hello\n",
        "is_error": false,
        "volatile_fields": ["content.timestamp"]
      }
    }
  ]
}
```

### 5.2 第二层：协议级契约测试（JSON-Lines）

**目标**：Java 后端产生的 BackendEvent JSON 与 Python 后端对 TypeScript 前端完全兼容。

**方法**：
1. 定义约 15 个会话场景（简单回复、工具调用、权限审批、错误、压缩等），每个场景覆盖 2-4 种 BackendEvent 子类型。
2. 用 Python 后端运行场景，录制完整 JSON-Lines 输出作为 golden file。
3. 用 Java 后端运行相同场景，逐行对比 JSON。
4. 使用语义比对而非字符串比对：忽略 `sessionId`、`timestamp` 等 volatile 字段，只比对结构和业务字段。
5. 所有 17 种 BackendEvent 子类型必须至少被一个场景覆盖。

**产出**：`tests/equivalence/protocol/` 下 15+ 个 golden file（`.jsonl`）及对应的场景定义。

### 5.3 第三层：Agent 循环行为对比

**目标**：相同消息序列 → 相同的工具调用序列和最终响应。

**方法**：
1. Mock LLM API（WireMock），返回预定义的 tool_use 响应。
2. 构造标准消息序列（含文本、工具调用、工具结果）。
3. 分别运行 Python 版和 Java 版 Agent 循环。
4. 对比：消息列表演化轨迹（追加顺序、content block 类型和内容）、工具调用顺序和参数、流式事件序列。
5. 差异分类为：逻辑差异（必须修正）vs 时序差异（Virtual Threads 调度顺序可接受，但工具执行结果必须一致）。

### 5.4 第四层：集成场景端到端对比

**目标**：真实 LLM API 的端到端行为一致。

**方法**：
1. 从 Python 测试套件中选取 10 个已有 E2E 场景（覆盖：纯文本对话、单工具调用、并行多工具、权限审批、自动压缩触发、Agent 子进程调度）。
2. 对每个场景，用相同 API key 依次运行 Python 和 Java 实现。
3. 非确定性容忍策略：LLM 输出文本允许语义等价而非字面一致，但工具调用必须精确匹配（工具名、参数 JSON 完全一致）。
4. 统计通过率和回归趋势。

### 5.5 验证节奏

| 阶段 | 验证层 | 触发时机 |
|------|--------|---------|
| 开发期 | 第一层（工具 I/O） | 每个工具实现完成时 |
| 集成期 | 第二层（协议契约） | UI 层对接前 |
